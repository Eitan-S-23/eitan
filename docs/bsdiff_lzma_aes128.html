Project Overview

BSDIFF + LZMA + AES128

一套完整的固件更新差分压缩加密系统，集成了业界标准的二进制差分算法(BSDIFF)、高效的LZMA压缩算法和军用级AES-128-CTR加密。 专为嵌入式设备和MCU固件OTA(Over-The-Air)更新设计，提供最小补丁体积、安全传输和灵活的部署方案。

BSDIFF 二进制差分 LZMA 高效压缩 AES-128-CTR 加密 MCU 嵌入式支持 CRC32 完整性校验 流式处理 可配置参数 Windows GUI
系统分为两个核心部分：bsdiff（差分压缩加密）和bspatch（解密解压还原）， 形成完整的编码-解码流程，支持多个MCU平台（STM32、ESP32、NRF52、GD32等）。

BSDIFF：差分压缩加密程序

bsdiff 程序负责将旧文件和新文件进行比较，生成最小化的补丁包。 整个过程分为三个关键步骤，每一步都是独立的、可配置的处理阶段。

完整处理流程

1
读取文件
将旧文件和新文件完全加载到内存中，为后续处理做准备
2
二进制差分（BSDIFF）
分析两个文件的差异，生成包含所有变化信息的差分数据
3
LZMA 压缩
对差分数据进行高效压缩，显著减小补丁文件体积
4
AES-128-CTR 加密
对压缩后的补丁进行加密，确保安全传输和版权保护
5
生成补丁文件
输出最终的加密补丁包，包含头部信息和完整的补丁数据

步骤 1：二进制差分（BSDIFF）

BSDIFF 算法是二进制差分的行业标准，它通过分析两个文件的字节级差异来生成高效的补丁数据。

算法原理

BSDIFF 算法采用扫描算法，核心思路是：

1
构建后缀数组 — 对旧文件构建后缀数组和后缀树，支持快速的子串匹配
2
扫描新文件 — 逐字节扫描新文件，寻找在旧文件中的最长匹配段
3
生成三类控制块 — 记录匹配段长度、新增数据长度、位置跳转值
4
输出补丁数据 — 包含控制块、旧文件差分数据、新增数据三部分

补丁数据结构

BSDIFF 生成的补丁包含三类数据流：

数据类型用途内容
控制块指导还原过程匹配长度、新增长度、位置偏移
差分数据与旧文件比较(新文件字节 - 旧文件字节)的差值
新增数据完全新增内容新文件中旧文件没有的字节

代码示例

// bsdiff/main.c - 差分创建流程
int bsdiff(const uint8_t* old, int64_t oldsize,
           const uint8_t* new, int64_t newsize,
           struct bsdiff_stream* stream);

// 使用示例
FILE *temp_diff_file = fopen(TEMP_DIFF_FILE, "wb");
stream.malloc = malloc;
stream.free = free;
stream.write = file_write;
stream.opaque = temp_diff_file;

if (bsdiff(old_data, old_size, new_data, new_size, &stream)) {
    fprintf(stderr, "bsdiff failed\n");
    return 1;
}
// 差分数据已写入临时文件
fclose(temp_diff_file);
BSDIFF 的关键优势是生成的补丁极小，通常只有文件大小变化部分的几个百分比。 后续的 LZMA 压缩进一步减小体积，最终补丁通常只需原文件 1-5% 的大小。

步骤 2：LZMA 压缩

LZMA(Lempel-Ziv-Markov Chain)是一种高效的数据压缩算法，特别适合嵌入式系统。 在本项目中，LZMA 对 BSDIFF 输出的补丁数据进行二次压缩。

压缩参数配置

LZMA 的压缩效果和性能受以下参数影响：

参数范围默认值说明
lc0-82Literal Context bits - 增大提高压缩率但耗费内存
lp0-40Literal Position bits - 与 lc 一起决定处理效率
pb0-40Position Bits - 位置编码的位数
fb5-27364Fast Bytes - 寻找匹配串的最大长度
dictSize1KB+4KB字典大小 - MCU 环境推荐 4-16KB
algo0-11算法选择：0=快速，1=正常

压缩过程

1
分配缓冲区 — 为压缩后的数据分配足够的内存
2
初始化编码器 — 设置 LZMA 属性（lc/lp/pb 等），创建编码环境
3
执行压缩 — 对差分数据进行编码，输出压缩数据和 LZMA 属性头
4
保存头部 — 记录 LZMA 属性和原始大小供解压使用

// 执行压缩

    compressedBuffer, &compressedSize,      // 输出：压缩数据和大小
    temp_buffer, diff_size,                 // 输入：差分数据和大小
    &props, header.ph_lzma_props, &propsSize,

printf("Compressed from %lld to %zu bytes\n", diff_size, compressedSize);
LZMA 压缩速度取决于 dictSize 和压缩级别。对于 MCU 环保系统，推荐 dictSize 为 4-16KB， 以平衡压缩率和解压时的内存占用。

步骤 3：AES-128-CTR 加密

AES-128-CTR 是高级加密标准(AES)在计数器(CTR)模式下的实现，提供流密码的灵活性和 AES 的安全性。 CTR 模式特别适合不同长度的数据加密，无需填充。

CTR 模式工作原理

CTR 模式(Counter Mode)将加密分为两个阶段：

1
Nonce + Counter — 生成 12 字节随机 Nonce 和 4 字节计数器初值，合成 16 字节初值
2
加密计数器 — 用密钥加密初值，生成密钥流
3
XOR 平文 — 将密钥流与平文 XOR，得到密文
4
4
计数器递增 — 每次加密 16 字节后，计数器递增，重复步骤 2-4

加密文件格式

加密补丁文件的结构：

部分大小内容
Nonce + Counter16 字节随机 Nonce（12 字节）+ 初始计数器（4 字节，通常为 0）
加密数据可变LZMA 压缩后的补丁数据，使用 AES-CTR 加密

加密参数

参数值说明
密钥16 字节AES-128 密钥（128 位），固定密钥或从配置获取
密钥类型对称加密和解密使用同一密钥
Nonce12 字节密码学安全随机数，每次加密不同
计数器4 字节通常初始化为 0，随数据加密而递增

代码示例

// bsdiff/main.c - AES-128-CTR 加密流程
void Aes128_Ctr(char *patch, char *encrypt) {
    // 固定密钥（应从安全源获取）
    uint8_t key[16] = {
        0x2b, 0x7e, 0x15, 0x16, 0x28, 0xae, 0xd2, 0xa6,
        0xab, 0xf7, 0x15, 0x88, 0x09, 0xcf, 0x4f, 0x3c
    };

    // 生成随机 Nonce（12 字节）和初始计数器（4 字节为 0）
    uint8_t nonce_counter[16];
    // Windows: CryptGenRandom()，Linux: /dev/urandom
    generate_random_nonce(nonce_counter, 12);
    nonce_counter[12] = nonce_counter[13] = 0;
    nonce_counter[14] = nonce_counter[15] = 0;

    // 初始化 AES 上下文
    AES_ctx ctx;
    AES_init_ctx(&ctx, key);

    // 打开输入文件（压缩后的补丁）
    FILE *infile = fopen(patch, "rb");
    FILE *outfile = fopen(encrypt, "wb");

    // 先将 nonce_counter 写入文件头（16 字节）
    fwrite(nonce_counter, 1, 16, outfile);

    // 读取、加密并写入数据
    uint8_t buffer[256];
    size_t bytes_read;
    while ((bytes_read = fread(buffer, 1, sizeof(buffer), infile)) > 0) {
        // CTR 模式加密（加密和解密操作相同）
        AES_CTR_encrypt(&ctx, buffer, bytes_read, nonce_counter);
        fwrite(buffer, 1, bytes_read, outfile);
    }

    fclose(infile);
    fclose(outfile);
}
AES-CTR 的优势：
• 流密码特性 — 不需要填充，适合任意长度数据
• 平行化 — 每个块可独立加密，支持并行处理
• 安全性 — 军用级加密标准，256 位等效强度（AES-128）

校验机制

补丁文件使用多层校验确保完整性：

1
头部 CRC — 验证头部本身未损坏，保护所有元信息
2
旧文件 CRC — 验证输入文件是否与预期匹配
3
新文件 CRC — 验证还原后的文件完整性

BSPATCH：解密解压还原程序

bspatch 程序负责将加密补丁还原为新文件，过程完全逆向于 bsdiff，分为三个对应的解码步骤。

完整处理流程

1
读取补丁文件
将加密补丁完全或流式加载，检查文件头部信息
2
AES-128-CTR 解密
检测加密标志，若加密则使用密钥和 Nonce 解密压缩数据
3
LZMA 解压
使用头部保存的 LZMA 属性，流式解压差分数据
4
二进制还原（BSPATCH）
逐块读取旧文件，应用解压后的差分数据生成新文件
5
校验验证
计算生成文件的 CRC，与头部数据对比验证完整性

步骤 1：AES-128-CTR 解密

bspatch 首先检查补丁文件是否加密，若加密则使用相同的密钥和 Nonce 解密。 CTR 模式的特性使得解密过程与加密完全相同。

解密检测机制

程序通过文件名自动检测加密状态：

// bspatch/main.c - 加密检测
is_encrypted = (strstr(argv[3], "_encrypt") != NULL);

if (is_encrypted) {
    printf("Detected encrypted patch file, decrypting with AES-128-CTR...\n");
    // 执行解密流程
}

解密过程详解

1
读取 Nonce — 从文件头部读取前 16 字节（12 字节 Nonce + 4 字节初始计数器）
2
初始化上下文 — 用固定密钥初始化 AES 上下文
3
逐块解密 — 读取加密数据，用相同的 Nonce 和 CTR 模式解密
4
保存解密结果 — 生成临时文件或内存缓冲保存解密后的压缩数据

代码示例

// bspatch/main.c - AES-128-CTR 解密
const uint8_t key[16] = {
    0x2b, 0x7e, 0x15, 0x16, 0x28, 0xae, 0xd2, 0xa6,
    0xab, 0xf7, 0x15, 0x88, 0x09, 0xcf, 0x4f, 0x3c
};

if (is_encrypted) {
    // 读取加密文件
    uint8_t *encrypted_data = malloc(encrypted_file_size);
    fread(encrypted_data, 1, encrypted_file_size, patch_file);
    fclose(patch_file);

    // 提取 Nonce 和计数器（前 16 字节）
    uint8_t nonce_counter[16];
    memcpy(nonce_counter, encrypted_data, 16);

    // 初始化 AES 上下文
    AES_ctx ctx;
    AES_init_ctx(&ctx, key);

    // 解密数据（从第 17 字节开始）
    size_t decrypted_size = encrypted_file_size - 16;
    uint8_t *decrypted_data = malloc(decrypted_size);
    memcpy(decrypted_data, encrypted_data + 16, decrypted_size);

    // CTR 模式解密（与加密相同操作）
    AES_CTR_decrypt(&ctx, decrypted_data, decrypted_size, nonce_counter);

    // 现在 decrypted_data 包含 LZMA 压缩的补丁数据
}
CTR 模式的对称性：加密和解密使用相同的操作，只需保存和还原 Nonce 和初始计数器值。 这比 CBC、ECB 等模式更简洁，且支持流式处理。

步骤 2：LZMA 解压

LZMA 解压是最复杂的步骤，特别在 MCU 环境中需要流式处理以节省内存。 程序使用从补丁头部提取的 LZMA 属性进行解压。

解压配置

从补丁头部提取解压所需信息：

信息来源用途
LZMA 属性ph_lzma_props (5 字节)恢复 lc/lp/pb 等参数
原始大小ph_original_size (8 字节)分配解压缓冲区，防止越界
压缩大小ph_psize (4 字节)读取压缩数据的范围

流式解压流程

1
初始化解码器 — 用 LZMA 属性初始化解压上下文和状态机
2
创建虚拟文件 — 为了兼容 Windows，使用虚拟文件结构而非 fmemopen
3
分块读取 — 每次读取固定大小（通常 1024 字节）的解压数据块
4
需要时解压 — BSPATCH 应用阶段按需调用解压函数获取数据

代码示例

// bspatch/user/interface.c - LZMA 流式解压初始化
vFile *vf = vfopen(patch_data, patch_size);
if (!vf) return 1;

// 准备 LZMA 头部（属性 + 原始大小）
uint8_t header_with_props[LZMA_PROPS_SIZE + 8];
memcpy(header_with_props, header.ph_lzma_props, LZMA_PROPS_SIZE);

// 复制原始大小（8 字节，小端）
for (int i = 0; i < 8; i++) {
    header_with_props[LZMA_PROPS_SIZE + i] =
        (header.ph_original_size >> (i * 8)) & 0xFF;
}

// 初始化解压器
vFile *header_vf = vfopen(header_with_props, sizeof(header_with_props));
int init_result = lzma_decompress_read(header_vf, NULL, 0);
vfclose(header_vf);

if (init_result < 0) {
    fprintf(stderr, "Failed to initialize LZMA decompressor\n");
    return 1;
}

// 后续按需调用 lzma_decompress_read() 获取解压数据

内存优化策略

对于内存受限的 MCU 环境：

1
缓冲区大小 — 通常设为 1KB-2KB（取决于 MCU RAM）
2
流式读取 — 不加载整个压缩文件，只加载必要的数据块
3
3
直接写入 Flash — 解压后的数据直接写入 MCU Flash，无需二次缓存
LZMA 解压耗时取决于数据大小和 dictSize，通常比加密耗时更长。 对于数 MB 文件，解压可能需要数秒到数十秒。

步骤 3：二进制还原（BSPATCH）

BSPATCH 算法应用 BSDIFF 生成的补丁，结合旧文件数据和补丁中的差分、新增数据， 逐块生成新文件。这是一个计算密集但 I/O 高效的过程。

还原原理

BSPATCH 通过三类数据的组合重建新文件：

操作类型输入处理输出
差分段旧文件 + 差分值逐字节相加新文件的对应段
新增段来自补丁的新数据直接复制新文件的新增部分
位置跳转控制块中的偏移调整旧文件指针下一个匹配位置

逐块处理流程

1
读取控制块 — 从解压流中读取 24 字节（3 个 8 字节值）
2
处理差分段 — 按控制块的第一个值，读取补丁数据，加上旧文件对应字节
3
处理新增段 — 按控制块的第二个值，直接复制补丁中的新增数据
4
调整指针 — 按控制块的第三个值调整旧文件读指针，重复直到新文件完成

代码示例

// bspatch/user/interface.c - 二进制还原核心逻辑
int chunked_bspatch(uint8_t *old_data, int64_t old_size,
                    uint8_t *new_data, int64_t new_size,
                    uint32_t newfile_addr,
                    struct bspatch_stream *stream) {
    uint8_t buf[8];
    int64_t oldpos = 0, newpos = 0;
    int64_t ctrl[3];  // [0]=diff_len, [1]=extra_len, [2]=seek_offset

    while (newpos < new_size) {
        // 读取控制块（3 个 8 字节值）
        for (i = 0; i <= 2; i++) {
            if (stream->read(stream, buf, 8)) return -1;
            ctrl[i] = offtin(buf);
        }

        // 处理差分段：新文件 += (旧文件 + 差分值)
        for (int64_t i = 0; i < ctrl[0]; i++) {
            if ((oldpos + i >= 0) && (oldpos + i < old_size)) {
                new_buffer[i] = old_data[oldpos + i] +
                               patch_buffer[i];  // 加上差分值
            }
        }
        // 写入新文件
        fwrite(new_buffer, 1, ctrl[0], newfile);

        newpos += ctrl[0];
        oldpos += ctrl[0];

        // 处理新增段：直接复制新增数据
        for (int64_t i = 0; i < ctrl[1]; i++) {
            stream->read(stream, &new_buffer[i], 1);
        }
        fwrite(new_buffer, 1, ctrl[1], newfile);

        newpos += ctrl[1];

        // 调整旧文件指针
        oldpos += ctrl[2];
    }

    return 0;
}

性能考量

在 MCU 环境中的优化：

1
缓冲处理 — 缓存块大小 256-1024 字节，平衡 RAM 和性能
2
Flash 写入 — 检查地址对齐，进行批量擦写以提高效率
3
串行处理 — 避免大量内存分配，使用链式处理各阶段
BSPATCH 应用的关键优势：
• 顺序处理 — 从前到后顺序应用补丁，支持流式处理
• 空间高效 — 只需保存一个控制块和缓冲区大小的内存
• 验证内置 — 通过多层 CRC 检查保证完整性

步骤 4：校验验证

补丁应用完成后，通过 CRC32 校验验证新文件的完整性，确保还原过程无错误。

三级校验机制

1
头部完整性
验证 ph_hcrc，检查补丁头部未损坏
2
旧文件验证
计算旧文件 CRC，与 ph_ocrc 对比，确保补丁匹配
3
新文件验证
计算生成文件 CRC，与 ph_ncrc 对比，确保还原正确

代码示例

// bspatch/main.c - 多层校验
// 1. 验证头部 CRC
uint32_t original_hcrc = header.ph_hcrc;
header.ph_hcrc = 0;
uint32_t calc_crc = crc32((const unsigned char *)&header,
                          sizeof(patch_header_t));
if (BigtoLittle32(original_hcrc) != calc_crc) {
    fprintf(stderr, "Corrupt patch file (invalid header CRC)\n");
    return 1;
}
header.ph_hcrc = original_hcrc;

// 2. 验证旧文件 CRC
uint8_t *old_data = read_entire_file(argv[1], old_size);
calc_crc = crc32(old_data, old_size);
if (BigtoLittle32(header.ph_ocrc) != calc_crc) {
    fprintf(stderr, "Old file CRC mismatch\n");
    return 1;
}

// 3. 应用补丁后，验证新文件 CRC
bspatch_patch(header, old_data, old_size,
              patch_data, patch_size, 0, new_data, new_size);

calc_crc = crc32(new_data, new_size);
if (BigtoLittle32(header.ph_ncrc) != calc_crc) {
    fprintf(stderr, "New file CRC mismatch (patch process failed)\n");
    return 1;
}

printf("Successfully applied patch: %s created\n", argv[2]);

BSDIFF 算法详解

BSDIFF 是 Colin Percival 在 2003 年提出的二进制差分算法，在业界广泛应用于版本控制、系统更新等领域。

核心思想

BSDIFF 的核心是利用后缀树/后缀数组加速匹配：

1
预处理 — 构建旧文件的后缀数组结构，支持 O(log n) 子串查询
2
扫描 — 从新文件起点扫描，在旧文件中二分查找最长匹配
3
编码 — 记录匹配信息（长度、新增数据长度、位置跳转）
4
输出 — 写入控制块、差分数据、新增数据

优势与限制

方面优势限制
补丁大小极小，通常 1-5% 原文件需要完整文件在内存中
性能O(n log n) 复杂度，快速无法处理超大文件
应用场景固件、软件更新、版本控制不适合数据库增量同步
兼容性算法稳定成熟，广泛使用不同版本可能不兼容

LZMA 压缩算法

LZMA(Lempel-Ziv-Markov Chain)由 Igor Pavlov 提出，基于 LZSS 和算术编码，提供业界最高的压缩率。

两阶段处理

1
LZ77 编码 — 寻找重复的字符串，用距离和长度替代
2
算术编码 — 对 LZ77 输出进行逐比特编码，达到最优压缩

AES-128-CTR 加密

AES(Advanced Encryption Standard)是美国联邦标准，CTR(Counter)模式将分组密码转换为流密码。

安全性分析

1
密钥强度 — 128 位密钥，2^128 搜索空间，现实中不可破解
2
Nonce 作用 — 12 字节随机 Nonce 确保相同明文产生不同密文
3
CTR 模式 — 抗性强，不存在 ECB 的相同明文块产生相同密文的弱点

注意事项

关键警告：
• 永不重用 Nonce —— 相同 Nonce + 密钥会导致整个安全性崩溃
• 保护密钥 —— 密钥应存储在安全区域（MCU 的 OTP、Secure Enclave 等）
• 随机数源 —— 使用密码学安全的随机数生成器
