🔄 OTA升级核心流程

💡 流程说明：
• 蓝色阶段（步骤1-6）：运行在App中，负责接收和存储升级包，以及更新AT24C02标志
• 黄色阶段（步骤7-11）：运行在Bootloader中，负责读取标志、升级和校验
• 🔴 关键步骤5（红框）：更新AT24C02中的升级状态和尝试次数，防止升级丢失
• 关键转折点：第11步的CRC32校验决定升级成功还是失败，失败时尝试次数递减
• 防死循环：尝试次数耗尽则放弃升级，避免Bootloader陷入无限重试

✅ CRC32校验与自动回滚

⚠️ 关键设计： 升级的安全性完全依赖CRC32校验。只有校验通过，Bootloader才会切换到新App，否则自动回滚。

📝 AT24C02 OTA参数存储结构

升级前状态
ota_state = IDLE
target_version = 0
retry_count = 0
active_partition = 1
App中更新（步骤5）
ota_state = UPGRADING
target_version = 2.0
retry_count = 3（重试次数）
active_partition = 1（保持不变）
升级成功（CRC✓）
ota_state = SUCCESS
target_version = 2.0
retry_count = 0
active_partition = 2（已切换！）
升级失败（CRC✗）
ota_state = FAILED
target_version = 2.0
retry_count = 2（递减）
active_partition = 1（保持原App）
💡 AT24C02存储策略：
• ota_state：升级状态机（IDLE=空闲、UPGRADING=升级中、SUCCESS=成功、FAILED=失败）
• retry_count：剩余尝试次数（建议初值=3）。每次失败递减，达到0则放弃升级，防止无限重试
• target_version：升级的目标版本号，用于标识升级目标
• active_partition：当前活跃分区（1=App1、2=App2），升级成功时才更新
• 这些参数在App的步骤5更新，Bootloader的步骤7读取，确保即使断电也能恢复状态
✓ 回滚保护： 新App写入失败不会影响原App，系统自动回退，用户无感知继续使用原版本，下次升级时重试

🔀 主备分区切换示例

升级场景演示：App1为活跃分区，升级到新版本v2

📌 升级前状态
App1 v1.0 活跃
App2 v0.9（旧版） 备用
• 当前运行：App1 v1.0
• 备用分区：App2 v0.9（可回滚）
📌 升级后状态（成功）
App1 v1.0（旧版） 备用
App2 v2.0 活跃（已切换）
• 当前运行：App2 v2.0（新版）
• 备用分区：App1 v1.0（可回滚）

升级失败场景

⚠️ CRC校验失败：
假设新App2 v2.0写入时部分bit翻转，CRC32不匹配
→ Bootloader检测失败
→ 不更改active_partition标志
→ 继续运行原App1 v1.0
→ App1显示升级失败提示，用户可重新尝试升级
